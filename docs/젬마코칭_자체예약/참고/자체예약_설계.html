손님이 시술을 고르면 들어갈 수 있는 시간만 보이는 예약

2차 논의에서 자체 예약을 만들기로 정했고, 3차 논의에서 네이버를 어떻게 남길지가 바뀌었습니다. 이 페이지는 무엇을, 왜, 어떤 순서로 만들지 정리한 설계안입니다. 1인이 바이브 코딩으로 만들고 운영한다는 조건에 맞춰 짰습니다.

정해진 것자체 예약 시스템. 11월 준비, 12월부터 단계적 시험
3차에서 바뀐 것네이버 예약은 끄지 않습니다. 노출을 지키려고 예약 상품은 켜 둔 채 마감하고, 안내 글과 링크로 자체 예약에 보냅니다

오버부킹은 지킬 조건이고, 풀어야 할 문제는 "찾기"와 "채우기"입니다

2차 논의에서 문제가 더 정확해졌습니다. 오버부킹은 핸드SOS가 이미 막고 있습니다. 손님과 원장님이 실제로 손해 보는 곳은 다른 데 있습니다.

손님 · 찾기

빈 시간을 못 찾고 포기

네이버는 날짜와 시간을 먼저 고르고 시술을 나중에 고릅니다. 시술이 안 맞으면 처음 화면으로 돌아갑니다. 예약이 일주일 넘게 밀려 있으면 날짜마다 눌러 보다 포기합니다.

원장 · 채우기

대기 수요가 있어도 빈자리

취소나 변경으로 생긴 자리를 알리는 길이 없어서, 기다리는 손님이 있는데도 그 시간이 비어 있습니다.

가게 · 지킬 것

동시 예약 0

손님의 상태를 먼저 읽고 제안하는 상담 방식이라 시선이 나뉘면 품질이 떨어집니다. 그래서 겹침은 어떤 경우에도 안 됩니다.

그래서 설계 원칙은 세 가지입니다.

  1. 시술 먼저, 그다음 들어갈 수 있는 시간만손님이 고른 시술의 길이로 계산해서 실제로 들어가는 시간만 보여 줍니다. 안 되는 시간은 아예 안 보입니다. 첫 화면에는 가까운 빈자리를 늘 띄워 둡니다(3차 논의).
  2. 겹침은 데이터베이스가 막는다화면 코드가 아니라 저장소 규칙이 겹치는 예약을 거절합니다. 1인 개발에서 동시에 두 명이 누르는 경우까지 코드로 완벽히 막기는 어렵습니다.
  3. 취소가 시스템 안에서 일어나게손님이 링크로 직접 취소하면 그 순간 시스템이 압니다. 원장님이 취소를 옮겨 적을 필요가 없어지고, 대기 자동 제안이 여기서 시작됩니다.

전체 구조도

달력은 하나, 원장님 카드와 손님 페이지가 같은 표를 봅니다

사라지는 것

원장님이 네이버·핸드SOS 예약을 카드 타임테이블에 손으로 옮겨 적는 일. 손님 예약이 바로 타임테이블에 뜨고, 전날 알림톡도 이 표에서 읽습니다.

그대로 쓰는 것

시술 시간표, 타임테이블 그리기, wait.html의 확인번호·하루 5번 제한·봇 거르기, 발송킹 연결, 상담 기록. 새로 배울 기술이 없습니다.

구체안 · 추천 스펙

항목마다 무엇을 고르고 왜 골랐는지

기술 묶음

지금 쓰는 것 그대로입니다. 정적 HTML + Vercel 서버 함수 + Supabase + 발송킹. 설치할 패키지도 새로 늘리지 않습니다.

왜으라 님이 이미 한 달 동안 82건을 이 묶음으로 만들었고 시험 281개가 돌아갑니다. Next.js 같은 새 틀로 옮기면 예약 기능보다 틀을 배우는 데 시간이 더 듭니다. 1인 개발에서 가장 큰 위험은 모르는 것을 동시에 두 개 배우는 것입니다.

원본 표 하나

손님 예약, 대기 손님에게 잡아 둔 자리, 원장님이 막은 시간(휴무·개인 일정)을 전부 card_bookings 한 표에 넣습니다.

create extension if not exists btree_gist;

create table card_bookings (
  id          bigint generated always as identity primary key,
  kind        text not null default 'booking',   -- booking 손님 예약 / block 원장이 막은 시간
  status      text not null default 'confirmed', -- held 잡아 둠 / confirmed 확정 / canceled 취소
  slot        tstzrange not null,                -- 시작~끝 (시술 분 + 정리 시간)
  service     text, minutes integer,
  name        text, phone text, customer_id bigint,
  token       text unique,                       -- 손님 개인 링크 열쇠, 무작위 32자
  hold_until  timestamptz, wait_id bigint,       -- 잡아 둔 자리가 풀리는 시각, 어느 대기 손님인지
  source      text not null default 'web',       -- web 손님 / card 원장 / naver 옮겨 적음
  created_at  timestamptz not null default now(),
  -- 잡아 둠·확정끼리는 1분이라도 겹치면 저장 자체가 거절된다
  exclude using gist (slot with &&) where (status in ('held', 'confirmed'))
);
alter table card_bookings enable row level security;  -- 손님은 직접 못 읽음, 서버 함수만
왜막아 둔 시간까지 같은 표에 넣어야 규칙 한 줄이 모든 겹침을 막습니다. 표가 나뉘면 "예약과 휴무가 겹치는지"를 코드로 따로 검사해야 하고, 그 검사가 빠지는 날 오버부킹이 납니다. source에 naver를 두는 이유는 전환 기간에 네이버 예약도 이 표에 옮겨 적어 같은 규칙으로 검사받게 하려는 것입니다.

들어갈 시간 계산

store.js에 순수 함수 하나를 더합니다. 화면도 서버도 모르는 함수라 node --test로 바로 시험할 수 있습니다.

// 시작 시각은 30분 간격으로 내되, 길이는 시술 시간 그대로 + 정리 시간
availableSlots({ bookings, hours, minutes: 120, buffer: 10, from: '2026-12-01', days: 14 })
// → [{ date: '2026-12-01', times: ['10:00', '14:30'] }, { date: '2026-12-02', times: [] }, ...]
  • 어떤 시각 t가 되려면 t부터 t + 시술 분 + 정리 시간까지가 영업시간 안이고, 잡아 둠·확정·막아 둠 어느 것과도 안 겹쳐야 합니다.
  • 영업시간·휴무일은 지금 카드에 없습니다(코드에는 10시~19시 고정). V0에서 설정으로 만듭니다.
  • 당일 예약은 지금부터 2시간 뒤부터만 냅니다. 원장님이 준비할 시간입니다.
왜"30분 남았는데 그 안에 들어가는 시술이 없어 예약이 막히는" 네이버의 문제를 손님이 겪지 않게 하려는 것입니다. 안 되는 시간은 처음부터 안 보이니 오류 화면이 생길 일이 없습니다. 계산을 순수 함수로 두면 "4시간 매직세팅 뒤에 커트가 들어가는가" 같은 경우를 시험으로 박아 둘 수 있습니다.

손님 예약 화면

첫 화면 가까운 빈자리→1 시술 고르기→2 조건 거르기 + 되는 시간→3 이름·번호·동의→완료 + 확정 문자
  • 첫 화면에 "가까운 빈자리"를 늘 띄웁니다. 커트·펌·염색처럼 분류마다 가장 가까운 시간 세 개씩. 손님 이름은 없고 시간만 보이니 인스타 스토리에 그대로 캡처해 올려도 됩니다(3차 논의: 남은 일정을 메인에 상시 노출).
  • 2단계는 날짜별로 묶어 한 화면에 보여 줍니다. 되는 시간이 없는 날은 "마감"으로 접습니다. 날짜마다 눌러 볼 필요가 없습니다.
  • 거르기 조건은 희망 달·평일/주말·오전/오후/5시 이후. 지금 wait.html의 조건과 똑같이 맞춥니다(3차 논의: 필터로 손님 조건을 받고 대기까지).
  • 거른 결과가 비면 "이 조건으로 대기 걸기" 단추 하나. 손님이 고른 시술과 조건이 대기 줄에 그대로 들어가서 다시 적을 필요가 없습니다.
  • 완료 화면에 "캘린더에 넣기" 버튼(.ics 파일). 네이버가 주던 캘린더 연동을 싸게 메웁니다.
  • 결제는 받지 않습니다. 지금처럼 매장에서, 정액권은 핸드SOS.
왜2차 논의에서 나온 손님 불편(날짜 먼저 고르기, 안 맞으면 처음으로, 날짜마다 조회)을 순서 하나로 뒤집습니다. 예약과 대기를 한 화면의 같은 조건으로 묶는 이유는 손님 입장에서 "원하는 시간을 찾다가 없으면 기다린다"가 한 흐름이기 때문입니다. 페이지가 둘이면 손님은 같은 조건을 두 번 적고, 원장님은 두 화면을 고쳐야 합니다. 결제를 빼는 이유는 온라인 결제를 붙이려면 결제 회사 계약·환불 규칙·정산까지 생겨서 1인 개발 범위를 넘기 때문입니다. 노쇼는 이미 있는 전날 알림톡으로 먼저 막고, 숫자를 본 뒤에 예약금을 다시 생각합니다.

손님 확인 방식

처음에는 로그인이 없습니다. 확정 문자에 손님마다 다른 링크(my.html?t=무작위 32자)가 들어가고, 그 링크로 예약 보기·취소·변경을 합니다. 인증번호 로그인은 V5에서 "내 시술 기록" 페이지와 함께 붙입니다.

왜2차 논의에서 나온 "전화번호 뒷자리로 로그인"은 그것만으로는 위험합니다. 뒷자리 4자리는 1만 가지라 이름과 함께 몇 번 시도하면 남의 예약을 열 수 있습니다. 예약 하나를 보는 데는 문자 속 긴 링크가 더 안전하고 만들기도 쉽습니다. 상담 기록처럼 민감한 것을 보여 줄 때는 문자 인증번호(6자리, 5분 유효, 하루 시도 제한)가 꼭 필요하니, 그 기능이 생기는 V5까지 미룹니다.

네이버 남기는 방식 (3차 논의)

3차 논의의 전제는 "네이버는 예약·페이를 쓰는 업체를 먼저 보여 준다"입니다. 그래서 예약을 그냥 끄면 노출을 잃을 수 있습니다. 논의에 나온 방식을 넷으로 나눠 비교했습니다.

방식네이버 노출겹침 위험정책 위험원장님 일
A 네이버 예약 끄기줄 수 있음없음없음없음
B 켜 두고 마감 + 안내·링크 (추천)예약 상품은 남음. 마감이 노출에 주는 영향은 V2에서 잼없음. 네이버로는 아무도 못 들어옴낮음. 플레이스·예약에 외부 링크를 건 사례가 제재 없이 돌고 있음처음 한 번 마감 설정, 안내 글 쓰기
C 빈 칸을 가짜 예약으로 채우기오를 수 있음없음높음. 없는 예약을 만드는 것이라 허위 예약으로 볼 수 있고, 제재받으면 평점 5점인 플레이스까지 잃음매번 채우고 지우기. 핸드SOS·카드 숫자도 오염
D 신규 첫 방문만 네이버에 열기유지있음. 네이버 예약을 표에 옮겨 적어야 함없음옮겨 적기가 계속 남음

B를 추천합니다. 네이버 예약 상품은 켜 둔 채 열린 칸 없이 마감하고, 예약 안내·플레이스 소식·인스타 프로필에 예약 페이지 링크를 겁니다. D는 V2에서 노출이 눈에 띄게 줄었을 때 꺼낼 대안으로 둡니다.

네이버 예약 안내·소식 글 초안헤어원네스트는 시술마다 걸리는 시간이 달라서, 시술을 먼저 고르면 들어갈 수 있는 시간만 보여 드리는 예약 페이지로 예약을 받고 있어요. 아래 링크에서 원하시는 시술을 고르시면 가장 가까운 빈자리가 바로 보여요. 원하는 시간이 없으면 대기를 걸어 두세요. 자리가 나면 문자로 먼저 알려 드려요.
왜손님은 미용실을 네이버 검색으로 찾으니 찾는 곳은 그대로 두고 예약하는 곳만 바꿉니다. C를 빼는 이유는 노출을 조금 얻는 대신 가게의 가장 큰 자산인 플레이스와 리뷰를 걸어야 하기 때문입니다(정책 원문은 확인 필요). 3차 논의에서 나온 "안내 글에 연락처를 걸고 손님이 직접 연락"은 원장님이 다시 중간에 끼는 길이라, 연락처 대신 예약 페이지 링크를 겁니다. 전환 기간에 같은 날을 네이버와 자체 예약이 함께 받으면 서로의 예약을 못 봐서 겹침이 다시 생깁니다. 그래서 V2~V3은 요일로 나눕니다.

  • 받는 것은 이름·번호·시술뿐. 동의 체크는 wait.html처럼 필수.
  • 개인정보처리방침 한 장을 예약 페이지 아래에 겁니다(수집 항목, 쓰는 곳, 보관 기간, 문자 발송 업체).
  • 손님 페이지는 다른 손님의 이름·시간을 절대 돌려주지 않습니다. 빈 시간만 돌려줍니다.
  • V5의 "내 시술 기록"에도 원장님의 진단 메모(얼굴형·모질 등)를 그대로 보이지 않습니다. 보여 줄 칸을 따로 정합니다.
왜2차 논의에서 개인정보 걱정이 나왔습니다. 처음부터 적게 받으면 지킬 것도 적습니다. 상담 기록은 원장님이 손님 앞에서 하는 말과 다르게 적힌 메모라, 그대로 보이면 관계를 해칠 수 있습니다.

버전 분할

버전마다 원장님이 써 볼 수 있는 것 하나로 끝냅니다

나누는 기준은 셋입니다. 버전이 끝나면 원장님이 직접 써서 확인할 수 있어야 하고, 손님이 보는 순간은 기초가 검증된 뒤여야 하고, 잘못되면 그 버전 전으로 되돌릴 수 있어야 합니다.

V1과 V2를 나눈 이유는 손님 화면의 불편과 실제 운영의 문제를 따로 보려는 것입니다. 대기(V3)를 실전(V2) 뒤에 둔 이유는 대기 자동 제안이 "손님이 링크로 취소한다"는 신호 위에서만 돌기 때문입니다. 전체 마감(V4)을 맨 뒤에 둔 이유는 노출이라는, 되돌려도 바로 회복되지 않는 것이 걸려 있기 때문입니다. V2에서 한 요일만 마감해 보고 노출 숫자를 먼저 재는 것이 3차 논의의 "마감하면 노출이 유지되나"라는 질문에 대한 가장 싼 답입니다. 그 요일은 언제든 다시 네이버에 열 수 있습니다.

순차 개발 방법

버전 하나를 이 여섯 걸음으로 돕니다

1 한 장 기획이 버전에서 원장님이 확인할 장면 하나를 글로
2 시험 먼저store.js 규칙은 시험이 빨간불부터
3 만들기작업 가지(branch)에서, 기능 하나마다 커밋
4 시험 모드?local=1로 가짜 손님으로 끝까지 눌러 보기
5 배포main에 합치면 Vercel이 올림
6 일주일 써 보기넘어가는 조건을 숫자로 확인
  • 클로드 코드에는 버전 단위로 시킵니다. "V1을 만들어 줘"가 아니라 "V1의 api/slots만, availableSlots 시험부터" 식으로 한 번에 한 파일씩.
  • 뼈대 검토는 V0 끝에 한 번 받습니다(2차 논의에서 말한 경은 님과의 골격 설계). 표 모양과 겹침 규칙은 손님 데이터가 쌓인 뒤엔 바꾸기 어렵기 때문입니다.
  • 프로젝트 CLAUDE.md에 "예약 넣기는 api/book.js 한 곳에서만", "card_bookings의 exclude 규칙을 지우지 않는다"를 규칙으로 적어 둡니다. AI가 다른 기능을 만들다 이 둘을 건드리지 않게 하려는 것입니다.

우려와 대응

2차 논의에서 나온 걱정마다 답을 붙였습니다

신규 손님이 새 예약 방식을 배워야 한다

대응화면을 세 단계로 줄이고, 단골이 V2~V3 동안 먼저 익숙해진 뒤 V4에서 신규에게 엽니다.

남는 위험네이버 예약 버튼에 익숙한 신규 손님 일부는 링크를 눌러 나가지 않고 이탈할 수 있습니다.

네이버가 주던 편의(검색·네이버페이·캘린더)를 잃는다

대응검색은 플레이스와 마감한 예약 상품을 남겨 유지, 캘린더는 .ics로, 결제는 원래 매장 결제라 잃는 것이 없습니다. 외부 링크는 제재 없이 돌고 있는 사례를 3차 논의에서 확인했습니다.

확인 필요마감 상태의 예약 상품이 검색 노출에 어떤 영향을 주는지. V2에서 한 요일로 직접 잽니다.

네이버 노출이 줄어든다 (3차 논의)

대응예약은 끄지 않고 마감(B안). 지금부터 스마트플레이스 통계의 주간 조회·예약 클릭을 적어 두고, V2 전후를 비교합니다. 줄었으면 신규 첫 방문만 네이버에 여는 D안으로 갑니다.

남는 위험"예약·페이 쓰는 업체를 먼저 보여 준다"는 전제 자체를 공식 자료로 확인하지 못했습니다. 숫자로만 판단할 수 있습니다.

개인정보

대응이름·번호·시술만 받고, 뒷자리 단독 로그인은 쓰지 않고, 기록 페이지는 인증번호를 붙이는 V5까지 미룹니다.

남는 위험개인 링크가 담긴 문자를 손님이 남에게 보내면 그 사람이 예약을 볼 수 있습니다. 링크로는 보기·취소만 되고 다른 정보는 안 보이게 합니다.

1인이 만들고 운영한다

대응겹침은 DB가 막고, 계산은 시험으로 박아 두고, 예약 페이지에 "안 되면 카톡 채널로" 안내를 고정합니다. 처음 화면에 "오늘 예약 N건" 확인 줄을 둡니다.

남는 위험Vercel·Supabase가 멈추면 그동안 예약이 안 들어옵니다. 무료 요금제의 Supabase는 일주일 안 쓰면 멈추는데, 매일 쓰는 가게라 해당은 적습니다.

전환 기간의 두 달력

대응요일로 나눕니다. 다른 요일의 네이버 예약도 이 표에 옮겨 적어 같은 규칙으로 검사받게 합니다.

남는 위험옮겨 적기는 V4 전까지 남습니다. 그래서 V2~V3를 길게 끌지 않습니다.

문자 비용

대응확정 문자 한 통에 개인 링크를 함께 넣습니다. 인증번호 문자는 V5부터라 그 전엔 늘지 않습니다.

남는 위험대기 제안은 취소 한 건에 최대 세 통이라 대기가 많으면 늘어납니다. 발송킹 잔액을 처음 화면에서 봅니다(이미 있음).
